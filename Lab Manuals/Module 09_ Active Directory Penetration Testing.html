Active Directory Penetration Testing

Scenario

Active Directory (AD) is a cornerstone of enterprise IT environments, managing user authentication, resource access, and organizational security policies. However, its complexity and widespread usage make it a prime target for attackers. A successful compromise of AD can lead to complete domain control, allowing attackers to exfiltrate sensitive data, disrupt operations, or escalate privileges across the network. Active Directory Penetration Testing identifies vulnerabilities, misconfigurations, and weaknesses within the AD environment before adversaries can exploit them. By simulating real-world attack scenarios, such as Kerberoasting, Pass-the-Hash attacks, and enumeration of domain trusts, organizations gain insights into their security gaps and actionable recommendations to strengthen their defenses.

The business value of Active Directory Penetration Testing lies in its ability to proactively reduce the risk of security breaches while ensuring compliance with regulatory requirements and cybersecurity best practices. Testing helps identify misconfigured permissions, unpatched vulnerabilities, and insecure protocols that could expose the domain to attacks. By addressing these issues, organizations safeguard their critical infrastructure, minimize downtime risks, and enhance their overall security posture. Investing in AD Penetration Testing demonstrates a commitment to cybersecurity resilience, protecting the organization’s reputation and ensuring the trust of stakeholders.

The Microsoft implementation of Kerberos can be slightly complicated, but the gist of the attack is that it takes advantage of legacy Active Directory support for older Windows clients, the type of encryption used, and the key material used to encrypt and sign Kerberos tickets. Essentially, when a domain account is configured to run a service in an environment such as MS SQL, a Service Principal Name (SPN) is used in the domain to associate the service with a login account. Exercise 7: Enumerating Unconstrained Delegation

In this lab, you will learn to enumerate and analyze unconstrained delegation settings and assess related security risks in Active Directory using PowerShell.

Prerequisites

Before starting this lab, you should understand Kerberos Authentication and Constrained and Unconstrained Delegation.

Kerberos Authentication

Kerberos provides secure authentication using tickets to prove identity instead of sending passwords over the network, reducing the risk of password theft. Kerberos authentication process is given below:

  • Step 1: When a user logs in, their password is converted into an NTLM. A timestamp is encrypted using this hash and sent to the Key Distribution Center (KDC) for verification.

  • Step 2: The KDC decrypts the message using the user's NTLM hash, then grants a TGT (ticket-granting ticket) encrypted with the domain controller's krbtgt account. This ticket is encrypted and can only be read by the domain controller (not the user).

  • Step 3: When the user requests access to a specific service, the KDC sends a TGS (ticket-granting service) encrypted with the NTLM hash of the requested service.

  • Step 4: The user presents the TGS to the service, which checks authorization and grants access if valid.

Constrained and Unconstrained Delegation

  • Delegation allows a service to act on behalf of a user to access other services without asking for the user's credentials again. For example, when a user logs into a web server, the web server needs to access a database on behalf of the user. Delegation allows the web server to impersonate the user and request access to the database.

  • In constrained delegation, the web server can impersonate the user only for specific services, which is a secure method. On the other hand, unconstrained delegation allows the web server to impersonate the user for any service in the domain, which can be exploited.

  • During Step 4 of Kerberos authentication, the domain controller (DC) checks if the web server has unconstrained delegation enabled. If enabled, the TGS (ticket-granting service) issued to the web server includes the user’s TGT (ticket-granting ticket). The web server can then extract the TGT and use it to request new tickets for other services on behalf of the user.

Exercise 8 : Launching Pass-the-Hash (PtH) Attack to Capture and Reuse Hashed Credentials

In the Pass-the-Hash (PtH) attack attackers capture and reuse hashed credentials (NTLM hashes) to authenticate without knowing the actual password. By exploiting vulnerabilities in Windows authentication protocols, attackers gain unauthorized access to network resources, enabling lateral movement within a network, often leading to significant security breaches.

The NTLM challenge sent during authentication can be responded to just by knowing the password hash. This means we can authenticate without requiring the plaintext password to be known.
